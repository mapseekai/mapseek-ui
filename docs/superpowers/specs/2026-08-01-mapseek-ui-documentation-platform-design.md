# Mapseek UI Documentation Platform Design

## Summary

Mapseek UI will replace its custom Vite Showcase with a bilingual, statically generated
Docusaurus documentation site. The site will document every public registry primitive and block,
embed the existing interactive examples directly in component pages, display the exact example
source, and publish the shadcn registry under the same domain.

The design follows the local `emap` project's conventions for Docusaurus packaging, Chinese and
English content, static deployment, and documentation verification. It intentionally differs from
`emap` by embedding examples in MDX pages instead of composing a separate examples application.

## Goals

- Provide Chinese and English documentation for every public registry item.
- Show installation, imports, interactive examples, source code, API guidance, accessibility
  notes, dependencies, and related components on each component page.
- Reuse all behavior currently covered by `showcase/src/showcases`.
- Publish the documentation and `/r/*.json` shadcn registry from one static deployment.
- Make missing translations, examples, registry entries, and links fail verification.
- Delete the old Showcase only after complete behavior and content parity is proven.

## Non-goals

- Publishing Mapseek UI as a runtime npm component package.
- Adding server-side rendering or a persistent application server.
- Generating exhaustive TypeScript API documentation in the first release.
- Adding Algolia or another hosted search dependency in the first release.
- Changing registry component behavior to accommodate the documentation site.

## Framework Decision

Use Docusaurus 3 with MDX.

Docusaurus fits the repository because it produces static output, renders React components in MDX,
and provides a first-party localization structure. It also matches the local `emap` documentation
platform. Astro Starlight would require an additional React-island hydration boundary around every
interactive example. Storybook Docs is optimized for a component workbench and iframe-based canvas,
not the requested integrated guide-and-example experience.

References:

- [Docusaurus MDX and React](https://docusaurus.io/docs/3.9.2/markdown-features/react)
- [Docusaurus configuration and i18n](https://docusaurus.io/docs/3.9.2/api/docusaurus-config)
- [Docusaurus deployment](https://docusaurus.io/docs/deployment)
- [Tailwind CSS with PostCSS](https://tailwindcss.com/docs/installation/using-postcss)

```text
mapseek-ui/

```

The root package becomes a Bun workspace containing `packages/*`. The docs package is private and
contains the Docusaurus dependencies. It imports current component implementations directly from
the root `registry/` directory through a configured alias.

The core new dependencies are:

- `@docusaurus/core`
- `@docusaurus/preset-classic`
- `@docusaurus/types`
- `@tailwindcss/postcss`
- `postcss`

## Routes and Localization

Chinese is the default locale and therefore has no locale prefix. English uses `/en`.

```text
/                              Chinese introduction
/getting-started/installation  Chinese installation guide
/components/button             Chinese primitive page
/blocks/layer-panel            Chinese block page
/en/                           English introduction
/en/components/button          English primitive page
/en/blocks/layer-panel         English block page
/r/button.json                 shadcn registry item
```

This follows the local `emap` Docusaurus localization model. The navbar contains documentation,
components, blocks, the language selector, theme control, and repository link. The docs plugin owns
the root route, and the blog plugin remains disabled.

Guide navigation is explicit in `sidebars.ts`. Component and block sections use autogenerated
sidebars based on their document directories and frontmatter ordering.

## Component Document Model

Every public registry item has one Chinese MDX document and one matching English MDX document.
Both documents use identical structural frontmatter:

```yaml
---
id: button
slug: /components/button
registryName: button
category: primitive
stability: stable
examples:
  - button/basic
  - button/variants
---
```

The following fields must match across languages:

- `id`
- `slug`
- `registryName`
- `category`
- `stability`
- `examples`

The title, description, prose, example labels, and accessibility notes are localized independently.

Each component page contains, in order:

1. Name and purpose
2. shadcn installation command
3. Basic import
4. Interactive examples
5. Exact example source
6. Common variants and usage guidance
7. Exports and important props
8. Accessibility guidance
9. Registry and npm dependencies
10. Related components

Registry manifests remain the source of truth for technical metadata: item name, English title and
description, dependencies, registry dependencies, and installation targets. MDX owns localized
explanation and usage guidance. Example files own executable behavior.

## Interactive Examples

Example code lives once under `packages/docs/src/examples`:

```text
src/examples/
├── button/
│   ├── basic.tsx
│   └── variants.tsx
└── layer-panel/
    └── basic.tsx
```

MDX imports both the component and its exact source:

```mdx
import { ComponentDemo } from "@site/src/components/ComponentDemo"
import { BasicButtonDemo } from "@site/src/examples/button/basic"
import basicSource from "@site/src/examples/button/basic.tsx?raw"

<ComponentDemo
  title="基础用法"
  component={BasicButtonDemo}
  source={basicSource}
/>
```

A Docusaurus Webpack rule maps the `?raw` resource query to Webpack's built-in `asset/source` type.
The preview and displayed source therefore cannot drift, and no raw-loader dependency is required.

`ComponentDemo` provides:

- Preview and source tabs
- Source copy action
- Example reset action
- Responsive preview sizing
- Light and dark theme synchronization
- `ConfirmProvider`
- Toaster support
- A portal-compatible DOM environment
- A per-example error boundary

An example failure is isolated to its demo surface and does not break the document page.

## Styling and Theme Integration

Docusaurus processes Tailwind CSS 4 through `@tailwindcss/postcss`. The documentation stylesheet
explicitly scans:

- `registry/**/*.{ts,tsx}`
- `packages/docs/src/**/*.{ts,tsx}`
- `packages/docs/docs/**/*.{md,mdx}`
- English MDX content

The existing generated Mapseek theme variables are loaded globally so examples render with the same
tokens as installed components. Docusaurus uses `data-theme="dark"`, while registry components use
the `.dark` variant. A small client module mirrors Docusaurus's current theme onto the root `.dark`
class. Docusaurus's `--ifm-*` variables remain separate from Mapseek's component tokens.

The documentation chrome uses Mapseek typography and primary accents while retaining Docusaurus's
layout primitives. Registry component implementations are not modified for documentation styling.

## Build and Deployment

The registry is built before Docusaurus. Docusaurus includes the root `public` directory as a static
directory, placing registry output in the final site without a second deployment.

```text
registry/*.json
      ↓ bun run registry:build
public/r/*.json
      ↓ Docusaurus staticDirectories
packages/docs/build/
├── index.html
├── components/
├── blocks/
├── en/
├── assets/
└── r/
```

The deployment publishes only `packages/docs/build`. Documentation, examples, and registry JSON are
therefore versioned and released atomically on one domain.

Root scripts follow the local `emap` naming conventions:

```json
{
  "docs:dev": "bun run registry:build && bun --cwd packages/docs run start",
  "docs:dev:en": "bun run registry:build && bun --cwd packages/docs run start -- --locale en",
  "docs:build": "bun run registry:build && bun --cwd packages/docs run build",
  "docs:serve": "bun --cwd packages/docs run serve",
  "docs:check-i18n": "bun scripts/check-docs-i18n.ts",
  "docs:check-examples": "bun scripts/check-docs-examples.ts",
  "docs:verify": "bun run typecheck && bun test && bun run registry:validate && bun run docs:check-i18n && bun run docs:check-examples && bun run docs:build"
}
```

## Migration Strategy

### Phase 1: Infrastructure

- Add the Bun workspace and private docs package.
- Configure Docusaurus, locales, routes, sidebars, Tailwind, aliases, and theme synchronization.
- Add installation and theming guides in both languages.
- Add `ComponentDemo` and documentation checks.
- Compose `/r` into the static output.

### Phase 2: Representative Components

Migrate three components before bulk conversion:

- Button: primitive, variants, and normal inline rendering
- Dialog: portals, providers, and interactive state
- LayerPanel: complex block behavior and responsive layout

These three establish the migration path for primitives, overlays, and complex blocks.

### Phase 3: Complete Migration

Move each current Showcase module into one or more focused example files. Every migrated item receives
its Chinese page, English page, registry mapping, and coverage validation in the same change.

Each existing Showcase initially becomes one `basic.tsx` example. High-value primitives such as
Button, Input, Select, and Dialog receive multiple focused examples in the first release. Additional
examples can be split later without changing the page architecture.

### Phase 4: Showcase Removal

Delete `showcase/`, its Vite configuration, and Showcase-specific scripts only after all public
registry items and all existing Showcase behaviors pass parity checks in the documentation site.

## Validation

### Content integrity

- Every public registry item has exactly one Chinese and one English page.
- Every page references an existing registry item.
- Paired pages have identical structural frontmatter.
- Every page declares at least one existing example.
- Every example belongs to exactly one public component page.
- Broken document and Markdown links fail the Docusaurus build.

### Code and build integrity

- TypeScript typecheck
- Biome checks
- Registry validation and build
- Docusaurus production build for both locales
- Verification that representative `/r/*.json` files exist in the final docs output

### Installation integrity

Existing shadcn installation verification remains authoritative. At minimum, one primitive and one
block are installed into clean Vite consumers, then typechecked and built.

### Interaction and visual integrity

The current Showcase visual QA becomes documentation visual QA. It covers:

- Chinese and English routes
- Light and dark themes
- Desktop and mobile viewports
- Button, Dialog, and LayerPanel baseline pages
- A render smoke check for every public component page

Interactive checks verify portals, dialogs, popovers, tooltips, toaster output, theme switching,
source tabs, copying, and reset behavior.

## Search

The first release provides a local filter on the component and block index pages. Full-text hosted
search is deferred until the public domain is stable. This avoids making the migration depend on an
Algolia account or external indexing service.

## Failure Behavior

- Missing registry metadata fails documentation validation.
- Missing translations or frontmatter mismatches fail bilingual validation.
- Missing examples or duplicate ownership fail example validation.
- Broken links fail the Docusaurus production build.
- A runtime example error is contained by `ComponentDemo` and remains visible to the reader.
- The old Showcase remains available until the new site proves complete parity.

## Completion Criteria

The migration is complete when all of the following are true:

- Every public primitive and block has complete Chinese and English documentation.
- Every current Showcase behavior has a corresponding embedded documentation example.
- Documentation and `/r/*.json` are emitted in one static build.
- Docusaurus builds both locales with no broken links.
- Real shadcn installation verification passes.
- Documentation interaction and visual QA pass.
- The old Showcase and all references to it are removed.
