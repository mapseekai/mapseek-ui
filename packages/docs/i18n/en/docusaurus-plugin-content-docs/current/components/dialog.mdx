# Dialog

Dialog is for short flows, confirmations, and local forms. It renders through a portal at the document root, so it is not clipped by demo containers, scrolling panels, or `overflow`, while keeping focus trapping, Escape close, and focus return to the trigger.

## Structure

`DialogContent` is the overlay container. It owns the portal, backdrop, max width, 16px padding, and section gap. Short content can use `title` and `description`; complex headings use `DialogHeader`, `DialogTitle`, and `DialogDescription`.

`DialogBody` contains the main content, and long content needs a body-level scroll boundary. `DialogFooter` stacks vertically on narrow screens and aligns actions to the end from `sm` upward. Business examples should not duplicate padding on the header or footer.

## Accessible Title

Every Dialog needs a readable title. Prefer `DialogContent title` or `DialogTitle`; the close button already includes screen-reader text. Do not make the title only decorative or rely on placeholder text.

## Dialog vs Sheet

Use Dialog for short confirmations, a few fields, and tasks that must block the current flow. Use Sheet for long forms, detail reading, batch editing, and content that needs frequent scrolling, because it preserves more context and gives the user a steadier scroll area.

## Accessibility

Trigger buttons should clearly name what they open. Close, cancel, save, and dangerous actions should be real `button` elements or `DialogClose`. Do not hide the main explanation inside the Dialog, and do not use color as the only state signal.
